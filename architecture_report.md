# Архитектурный отчёт: Sales & Marketing DWH

## 1. Цель и архитектура проекта

Цель проекта - разработка распределённого аналитического хранилища данных на базе Greenplum 7 для анализа продаж, клиентов, маркетинговых кампаний и эффективности рекламных каналов.

Хранилище реализовано по трёхслойной архитектуре **STG -> DDS -> CDM**.

- **STG** - слой исходных данных, содержащий пять таблиц: customers, channels, campaigns, orders и order_items. Сгенерировано 2714 записей.
- **DDS** - слой детализированных данных, состоящий из трёх измерений (dim_customers, dim_channels, dim_campaigns) и двух таблиц фактов (fact_orders, fact_order_items). Реализованы служебные поля load_dt и load_src.
- **CDM** - аналитическая витрина dm_sales_performance, содержащая агрегированные показатели продаж и маркетинга по датам и кампаниям.

Все данные являются синтетическими и генерируются средствами SQL.

## 2. Решения по распределению данных

При проектировании Greenplum учитывались размеры таблиц и характер аналитических запросов.

Для таблиц заказов и товарных позиций выбран **DISTRIBUTED BY (order_id)**. Использование одинакового ключа позволяет выполнять соединение этих таблиц локально на сегментах.

Небольшие справочники рекламных каналов и кампаний размещены с помощью **DISTRIBUTED REPLICATED**, поскольку содержат только 4 и 10 записей соответственно.

Для витрины CDM выбран **DISTRIBUTED BY (campaign_id)**. Это позволяет выполнять группировку по кампаниям без дополнительного перераспределения данных.

При проверке выявлен перекос распределения витрины: 3202 строки на первом сегменте и 944 строки на втором. Причина — низкая кардинальность ключа campaign_id.

Текущая стратегия сохранена ввиду небольшого объёма данных и преимуществ локальной агрегации. Для промышленной системы целесообразно экспериментально сравнить её с распределением по составному ключу.

## 3. Партиционирование

Для таблиц stg.orders, dds.fact_orders и cdm.dm_sales_performance реализовано годовое партиционирование по датам.

Созданы партиции за 2025 и 2026 годы.

При выполнении запроса с фильтрацией за 2026 год оптимизатор Greenplum прочитал только одну из двух партиций.

Это подтверждает работу механизма **Partition Pruning**, позволяющего исключать ненужные разделы таблиц.

## 4. Бизнес-метрики

Аналитическая витрина содержит 4146 строк и рассчитывает следующие показатели:

- Количество завершённых заказов - orders_count.
- Количество уникальных покупателей - customers_count.
- Выручка - revenue.
- Средняя сумма заказа - avg_order_amount.
- Количество новых клиентов - new_customers.
- Расчётные рекламные расходы - spend.
- Рентабельность маркетинговых затрат - ROI.

При расчётах учитываются только заказы со статусом completed.

Новым клиентом считается покупатель, совершивший свой первый завершённый заказ.

Поскольку исходные данные не содержат фактических рекламных затрат, показатель spend рассчитывается посредством равномерного распределения бюджета по дням действия кампании.

ROI рассчитывается по формуле:

**ROI = (Revenue - Spend) / Spend × 100%.**

Расходы и показатели рентабельности являются модельными, поэтому не предназначены для оценки реальных рекламных кампаний.

## 5. Результаты оптимизации

Для всех основных таблиц выполнен ANALYZE. Исследованы планы запросов с помощью EXPLAIN ANALYZE.

| Проверка | Полученный результат |
|---|---|
| Агрегация CDM с фильтром за 2026 год | 2,649 мс |
| Агрегация CDM без фильтра | 2,573 мс |
| Соединение таблиц фактов | 4,173 мс |
| Чтение партиций при фильтрации | 1 из 2 |
| Redistribute Motion при соединении фактов | Отсутствует |
| Распределение fact_orders | 302 / 298 |
| Распределение fact_order_items | 1005 / 995 |
| Распределение CDM | 3202 / 944 |

Планы запросов подтвердили использование оптимизатора GPORCA, локальных Hash Join и HashAggregate, а также Gather Motion для передачи результатов координатору.

Партиционирование успешно исключает ненужные разделы, однако на небольшом учебном наборе данных сокращение времени выполнения не было доказано. Для оценки реальной эффективности необходимы многократные измерения на более крупных объёмах.

Дополнительные индексы не создавались, поскольку для текущего объёма данных и характера аналитических запросов их необходимость не была подтверждена.

## 6. Итоговые результаты и выводы

В результате выполнения проекта построено аналитическое хранилище с тремя слоями и подготовлены четыре бизнес-отчёта.

По результатам проверок работающей базы:

- Загружено 600 заказов, из которых 420 завершены.
- Обработано 2000 товарных позиций.
- Определено 100 новых покупателей.
- Выручка составила 11 076 578,02 условных денежных единиц.
- Расчётные маркетинговые расходы составили 1 039 376,84 условных денежных единиц.
- Проверены согласованность сумм заказов, связи между таблицами и отсутствие дубликатов в CDM.

Созданы SQL-скрипты для развёртывания хранилища и повторного расчёта аналитических показателей.

**Вывод:** разработанная архитектура соответствует требованиям учебного проекта. Выбранные ключи распределения и партиционирование обеспечивают корректную работу аналитических запросов. Обнаруженный перекос в CDM является ограничением текущей модели и требует дополнительного исследования при увеличении объёма данных.

Окончательное подтверждение воспроизводимости предусматривает отдельное развёртывание проекта из подготовленных SQL-файлов на чистой базе данных.
